# PayEvo project summary

Prepared for leadership — 2026-08-20

## What was built

I developed a working internal prototype of a 2FA timetracker feature. It leverages a Hugging Face Computer Vision + Deep learning model to transform webcam taken images into embeddings that can be compared against a pre-loaded database of embeddings to validate user identity. There were 2 main pipelines in this software.

### Employee enrolment

First the "employee enrollment", that is a profile that contains a set of "embeddings", generated by the user when they upload pictures of their face into the feature.

1. An authenticated user creates or edits an `EmployeeProfile` through `/api/feature-a/employees`.
2. A photo is uploaded and sanitized before its `CameraCapture` record and stored image are created.
3. Linking the capture to an employee creates an `employee_face_library` entry and queues embedding/training work. We queue the training work so the user doesn't have to wait.
4. The embedding worker claims a job with `FOR UPDATE SKIP LOCKED`, calls the Python `/embed` endpoint, writes the normalized vector, and recomputes the employee centroid.

### Recognition

The second pipeline allowed the user to enter their pin, then be prompted to take a picture to validate their identity.

1. `/api/camera/recognize` sanitizes the image that was taken and asks the face-recognizer for an embedding.
2. The first path searches tenant- and model-specific employee centroids (stage A). Centroids are "averages" of all the individual embeddings that were generated in their profile. This is done to cut down on time.
3. After finding its best match, It searches individual enrolled vectors for the shortlisted employees (stage B), then applies confidence and ambiguity thresholds. We do this to confirm a strong enough match before we confirm to the user.
4. The route records an audit event and, when supplied, persists the result on the original camera capture.

## Research and technical decisions

- Utilized pre existing architecture that combines Next.js for the web/API layer, PostgreSQL with pgvector for data and similarity search, and a separate Python service for model inference.
- Implemented and investigated asynchronous processing so image upload and enrolment do not wait for ML inference.
- Developed a centroid-first recognition approach to improve recognition search scalability, with a second-stage vector comparison and confidence/ambiguity thresholds to reduce incorrect automatic matches.
- Investigated operational failure cases: removed photos leaving stale metadata, concurrent embedding work, unavailable inference, invalid/no-face images, camera-panel build errors, and `BigInt` compiler compatibility for the earlier image-hash approach.
- Incorporated security-oriented patterns: tenant scoping, permission helpers, audit logs, image re-encoding/sanitization, PIN hashing, feature flags, kill switches, request IDs, rate-limiting groundwork, and local Docker orchestration.

## What remains

The project is a development prototype, not a production-ready biometric system. The highest-priority work is replacing development authentication with the organization’s identity provider, completing legal/privacy and biometric governance, and validating model performance, fairness, spoof resistance, and human-review policy on approved representative data. To summarize, stress test the software to make it user proof.

Production deployment also needs managed infrastructure, secure durable image storage, secret management, monitoring/alerting, backups and restore tests, CI/CD, security scanning, a shared distributed rate limiter, migration rehearsals, and a tested rollback process. The active engineering branch/worktree changes must be triaged, tested, and committed before release planning. Full details are in [Handoff](Handoff.md), will be found in the repo once it is commited. It is important that the database technology used should be changed. PostgreSQL with pgvector is good, but a proper vector database technology would be better.
